Mockup 3 · Change Review

Diff, Git, Quality, Masking and environments already exist as separate tabs. This joins them into one "should this go to prod?" flow.
  1. A change is a thing. Branch + environment pair + description, so the question is "promote this change", not "run diff and eyeball it".
  2. Grouped by impact. Changed files first, then downstream models and dashboards that will move, then what the hash cache skips.
  3. Impact graph. Just the affected subgraph, not the whole DAG. Solid = edited, dashed = rebuilt as a consequence.
  4. Data diff, not only a code diff. Row add/remove/modify counts and schema changes from the existing 3-mode diff engine.
  5. Business impact. If a semantic-layer metric reads the model, show how it moves in dev vs prod. "−2.4% revenue" gets a reviewer's attention in a way "312 rows modified" doesn't.
  6. An explicit gate. Every check in one list. The disabled button says exactly why, and the promote plan (backup, build, assert, rollback) is spelled out before anyone clicks.
